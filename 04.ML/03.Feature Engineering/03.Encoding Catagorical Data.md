## 1.2 The problem

Machine learning algorithms do **mathematics**: distances, dot products, gradients, splits on thresholds. They need **numbers**. Real datasets, however, contain **string columns**:

|age|gender|review|education|purchased|
|---|---|---|---|---|
|24|Male|Good|UG|Yes|
|31|Female|Poor|School|No|
|45|Female|Average|PG|Yes|

Most scikit-learn estimators fail on such data:

```python
import pandas as pd
from sklearn.linear_model import LogisticRegression

X = pd.DataFrame({"age": [24, 31, 45], "review": ["Good", "Poor", "Average"]})
y = [1, 0, 1]
try:
    LogisticRegression().fit(X, y)
except ValueError as e:
    print(e)          # could not convert string to float: 'Good'
```

**Encoding** converts categories into numbers. The art is doing it **without injecting information that is not there** (a fake order, fake distances) and **without losing information that is there** (a real order).

## 1.3 Data types recap

|Type|Meaning|Examples|Typical handling|
|---|---|---|---|
|**Numerical**|quantifiable measurements|age, height, salary, price|scale (not encode)|
|**Nominal categorical**|categories with **no intrinsic order**|state (West Bengal, Maharashtra), engineering branch, gender, colour, city|One-Hot, frequency, target encoding|
|**Ordinal categorical**|categories with a **natural rank or order**|education (High School < Under Graduate < Post Graduate); rating (Poor < Average < Good < Excellent); T-shirt size (S < M < L < XL)|**Ordinal Encoding**|
|**Target label**|the class we predict|purchased (Yes / No), species, churn|**Label Encoding**|

# 2. Why arbitrary integers are dangerous (derivation)

The simplest idea is "give every category an integer". Whether that is acceptable depends on whether the integers **mean something**.

## 2.1 What integer codes tell a model

If a column is coded as $c \in {0, 1, 2, \dots, K-1}$, a model can use three properties:

1. **Order:** $0 < 1 < 2$.
2. **Spacing:** the gap between 0 and 1 equals the gap between 1 and 2.
3. **Magnitude:** 2 is "twice" 1.

For an **ordinal** variable, (1) is true, and (2) and (3) are reasonable approximations. For a **nominal** variable, none of them is true, so the encoding **invents structure**.

## 2.2 Linear models: forced equal steps

A linear (or logistic) model with one integer-coded feature predicts $$\hat{y} = b + w,c$$ The effect of moving from code $c$ to $c+1$ is **always $w$**, for every adjacent pair, in one direction. With states coded Bengal = 0, Maharashtra = 1, Delhi = 2, the model asserts that Delhi's effect is exactly twice Maharashtra's. There is **one parameter** for a variable that has $K$ separate groups.

One-hot encoding gives each category its own effect: $$\hat{y} = b + \sum_{k=1}^{K-1} w_k,\mathbb{1}[\text{category} = k]$$ $K - 1$ free parameters, so each category can sit at any level.

```python
import numpy as np
from sklearn.linear_model import LinearRegression
from sklearn.preprocessing import OneHotEncoder

rng = np.random.default_rng(0)
cat = rng.choice(["A", "B", "C", "D"], 2000)
means = {"A": 10, "B": 30, "C": 10, "D": 30}                       # no monotone pattern with the code order
y = np.array([means[c] for c in cat]) + rng.normal(0, 1, 2000)

codes = np.array([["A", "B", "C", "D"].index(c) for c in cat]).reshape(-1, 1)
ohe = OneHotEncoder(sparse_output=False).fit_transform(cat.reshape(-1, 1))

print("integer codes R2:", LinearRegression().fit(codes, y).score(codes, y).round(3))       # near 0 (no linear trend)
print("one-hot R2      :", LinearRegression().fit(ohe, y).score(ohe, y).round(3))           # about 0.98
```

With integer codes the model sees essentially nothing; with one-hot it fits almost perfectly. (If the real effects happened to rise steadily with the code, the integer version would do fine, which is exactly the **ordinal** case.)

## 2.3 Distance-based models: invented distances

KNN, K-Means and SVM use distances. With Bengal = 0, Maharashtra = 1, Delhi = 2:

- distance(Bengal, Maharashtra) = 1
- distance(Bengal, Delhi) = 2
- distance(Maharashtra, Delhi) = 1

The model believes Maharashtra is "between" Bengal and Delhi and that Delhi is twice as different from Bengal as Maharashtra is. If the code order had been alphabetical or random, those beliefs would change. None of this reflects reality.

## 2.4 Tree models: less harmed, not immune

A tree splits on thresholds ("code <= 1.5"). It can isolate any category with enough splits, so it copes better with integer codes, though it needs more splits for non-contiguous groups. Even so, the arbitrary code order influences which groups can be separated with one split.

## 2.5 The rule that follows

|Variable|Safe encoding|Why|
|---|---|---|
|**Ordinal**|integers **in the true order**|the order is real information|
|**Nominal**|One-Hot (or another non-ordinal encoding)|no order exists, so do not create one|
|**Target label**|integers (any consistent mapping)|the model only needs distinct classes; no ordering is used|

This is the entire reasoning behind the two tools in this note.

# 3. Classifying columns

## 3.1 A decision procedure

```
Is the column a number you can measure (age, salary)?  --> numerical (scale it)
Otherwise it is categorical. Ask:
  "Can I sort the categories in a meaningful, universal way,
   so that 'higher' really means more of something?"
     yes --> ORDINAL  (ordinal encoding with a custom order)
     no  --> NOMINAL  (one-hot etc.)
Is this the column we are predicting?  --> TARGET (label encoding)
```

## 3.2 Examples

|Column|Categories|Type|Plan|
|---|---|---|---|
|`education`|School, UG (under graduate), PG (post graduate)|ordinal|OrdinalEncoder|
|`review`|Poor, Average, Good|ordinal|OrdinalEncoder|
|`gender`|Male, Female|nominal (binary)|One-Hot (or 0/1)|
|`state`|West Bengal, Maharashtra, Delhi|nominal|One-Hot (or frequency / target if many)|
|`branch`|Civil, Mechanical, CS|nominal|One-Hot|
|`size`|S, M, L, XL|ordinal|OrdinalEncoder|
|`credit_rating`|AAA, AA, A, BBB, ... D|ordinal|OrdinalEncoder|
|`month`|Jan ... Dec|ordered but **cyclical**|sin/cos encoding, not plain ordinal|
|`purchased`|Yes, No|target|LabelEncoder|

## 3.3 Traps in classification

- **Numbers that are really categories:** `pincode`, `zip`, `user_id`, `phone_area_code`. They look numeric but carry no order. Treat them as nominal.
- **Categories that look ordered but are not:** blood type A, B, AB, O has no ranking.
- **Ordered but unevenly spaced:** Poor, Average, Good: is the gap Poor to Average the same as Average to Good? Often not. See section 4.8.
- **Cyclical order:** days of the week and months. Sunday (6) is next to Monday (0) in reality, but integer codes put them 6 apart.
- **Binary columns** (Yes/No, Male/Female) can simply be 0/1; they are both nominal and "ordinal" for free.

Use the bivariate tools from [[07.Bivariate and Multivariate Analysis]] to check: compute the target rate per category and see whether it moves steadily with the supposed order.

```python
df.groupby("review")["purchased"].apply(lambda s: (s == "Yes").mean()).reindex(["Poor", "Average", "Good"])
```

A steadily rising pattern supports an ordinal encoding; a zig-zag suggests one-hot even for an "ordered" column.

# 4. Ordinal Encoding (`OrdinalEncoder`)

## 4.1 What it does

`sklearn.preprocessing.OrdinalEncoder` converts **input feature columns** ($X$) from strings to integers, one integer per category. You can supply an **explicit order** so the integers reflect the real ranking.

```python
from sklearn.preprocessing import OrdinalEncoder
import numpy as np

X = np.array([["Good"], ["Poor"], ["Average"], ["Good"]])
oe = OrdinalEncoder(categories=[["Poor", "Average", "Good"]])
print(oe.fit_transform(X).ravel())          # [2. 0. 1. 2.]
```

Mapping: Poor = 0, Average = 1, Good = 2. The output is **float** (`2.0`) by default; use `dtype=int` to get integers if there are no missing values.

## 4.2 The default order is alphabetical, not logical

If you do not pass `categories`, scikit-learn sorts the categories **alphabetically**. For the review column that gives a wrong ranking.

```python
reviews = np.array([["Poor"], ["Average"], ["Good"]])

default = OrdinalEncoder().fit(reviews)
print(default.categories_)                               # [array(['Average', 'Good', 'Poor'], dtype=object)]
print(default.transform(reviews).ravel())                # Poor -> 2, Average -> 0, Good -> 1   (WRONG order)

custom = OrdinalEncoder(categories=[["Poor", "Average", "Good"]]).fit(reviews)
print(custom.transform(reviews).ravel())                 # Poor -> 0, Average -> 1, Good -> 2   (correct)
```

Under the alphabetical default, "Poor" would be rated higher than "Good". **Always pass `categories` for ordinal columns.**

## 4.3 The `categories` parameter: a list of lists

There is one inner list per column, **in the same order as the columns you pass in**. Each inner list is ordered from lowest to highest.

```python
oe = OrdinalEncoder(categories=[
    ["Poor", "Average", "Good"],          # for the 1st column: review
    ["School", "UG", "PG"],               # for the 2nd column: education
])
oe.fit_transform(X_train[["review", "education"]])          # column order must match the list order
```

If you swap the column order in the data but not in the list, the encoding is silently wrong. Select columns explicitly (`X_train[["review", "education"]]`) and keep the lists aligned.

## 4.4 Constructor options

```python
OrdinalEncoder(
    categories="auto",                  # or a list of lists
    dtype=np.float64,                   # output dtype
    handle_unknown="error",             # or "use_encoded_value"
    unknown_value=None,                 # code for unseen categories (when handle_unknown="use_encoded_value")
    encoded_missing_value=np.nan,       # code given to missing values
    min_frequency=None,                 # group rare categories (scikit-learn 1.3+)
    max_categories=None,                # keep only the top-N (scikit-learn 1.3+)
)
```

|Parameter|Use|
|---|---|
|`categories`|**the order**; also fixes the allowed categories|
|`handle_unknown="use_encoded_value"` with `unknown_value=-1`|unseen categories at prediction time get -1 instead of an error|
|`encoded_missing_value`|integer (or NaN) for missing values|
|`dtype=int`|cleaner integers (no missing values)|

## 4.5 Attributes after `fit`

```python
oe.categories_          # the categories used for each column, in encoded order
oe.feature_names_in_    # names of the fitted columns (if DataFrame input)
oe.n_features_in_
```

## 4.6 Methods

|Method|Purpose|
|---|---|
|`fit(X_train)`|learns the category-to-integer mapping from the **training** data (or validates the supplied `categories`)|
|`transform(X)`|converts strings to integers with that mapping (train, test, new data)|
|`fit_transform(X_train)`|both, for training data only|
|`inverse_transform(Z)`|integers back to the original strings|

```python
Z = oe.transform(X_test[["review", "education"]])
oe.inverse_transform(Z)            # back to 'Good', 'UG', ...
```

## 4.7 Alternatives in pandas

```python
# (a) dict mapping: explicit, transparent
rank = {"Poor": 0, "Average": 1, "Good": 2}
df["review_enc"] = df["review"].map(rank)                 # unseen label -> NaN (silent!)

# (b) ordered Categorical: keeps meaning and allows comparisons
df["review"] = pd.Categorical(df["review"], categories=["Poor", "Average", "Good"], ordered=True)
df["review"].cat.codes                                    # 0, 1, 2 (missing -> -1)
df["review"] > "Poor"                                     # True/False, uses the order

# (c) factorize with sort: order from the data, only alphabetical (avoid for ordinal columns)
codes, uniques = pd.factorize(df["review"], sort=True)
```

||`OrdinalEncoder`|`.map` / `Categorical`|
|---|---|---|
|Works in sklearn `Pipeline` / `ColumnTransformer`|**yes**|no (done outside)|
|Same mapping at prediction time|automatic (fitted object)|you must reuse the dict|
|Unknown category|error or chosen code|silent `NaN` or `-1`|
|Best for|modelling pipelines|quick exploration|

Because the mapping from a custom order list is deterministic and does not depend on the data, using a dictionary is not a leakage risk. Even so, `OrdinalEncoder` in a pipeline is the production-friendly choice.

## 4.8 Does the spacing make sense?

Integer codes assume **equal gaps** between consecutive categories. Often the real gaps differ (the jump from "Poor" to "Average" may matter less than from "Average" to "Good"). Options:

1. **Keep 0, 1, 2** (fine for trees and many practical cases).
2. **Custom numeric values** that reflect your domain knowledge:
    
    ```python
    review_score = {"Poor": 1, "Average": 3, "Good": 4}          # unequal spacing on purposedf["review_enc"] = df["review"].map(review_score)
    ```
    
3. **Data-driven spacing:** target encoding of the ordered categories (a later note), or treat the ordinal variable as nominal and one-hot encode it when the target pattern is not steady.
4. For a **linear** model, check that the target moves roughly linearly with the code; if not, one-hot is safer.

## 4.9 When to use ordinal encoding

- The feature is **ordinal** (education, rating, size, grade, severity, tier).
- Tree-based models can also use it for **high-cardinality nominal** columns as a quick baseline (with caution, since the order is arbitrary).
- You want **one column out** instead of K columns.

# 5. Label Encoding (`LabelEncoder`)

## 5.1 What it does

`sklearn.preprocessing.LabelEncoder` converts the **target variable $y$** from strings into integers $0, 1, \dots, K-1$. It is meant for **1-dimensional target labels** in classification.

```python
from sklearn.preprocessing import LabelEncoder

y = ["Yes", "No", "No", "Yes", "Yes"]
le = LabelEncoder()
y_enc = le.fit_transform(y)
print(y_enc)             # [1 0 0 1 1]
print(le.classes_)       # ['No' 'Yes']   -> No = 0, Yes = 1
print(le.inverse_transform([0, 1, 1]))     # ['No' 'Yes' 'Yes']
```

## 5.2 How the integers are assigned

Labels are **sorted alphabetically** and numbered from 0. There is no way to supply a custom order, and the target has no meaningful order anyway.

|Labels|Encoding|
|---|---|
|No, Yes|No = 0, Yes = 1|
|setosa, versicolor, virginica|0, 1, 2|
|Churn, Stay|Churn = 0, Stay = 1|

### Watch the positive class

Metrics such as precision, recall, and F1 treat class **1** as "positive" by default. With `['No', 'Yes']`, the positive class is Yes (good). With `['Churn', 'Stay']`, alphabetical order makes **Stay = 1**, so "positive" means _staying_, not churning, which is probably not what you want to detect.

```python
y = ["Stay", "Churn", "Stay", "Churn"]
print(LabelEncoder().fit(y).classes_)                           # ['Churn' 'Stay']  -> Stay = 1 (!)

y_enc = pd.Series(y).map({"Stay": 0, "Churn": 1})               # make the class of interest = 1 explicitly
```

For binary targets, an explicit mapping gives you control over which class is 1.

## 5.3 Methods and attributes

|Member|Purpose|
|---|---|
|`fit(y_train)`|learns the classes from the **training labels**|
|`transform(y)`|label strings to integers|
|`fit_transform(y_train)`|both, for training labels|
|`inverse_transform(codes)`|integers back to the original labels (use for readable predictions)|
|`classes_`|the sorted unique labels; `classes_[i]` is the label for code `i`|

```python
preds = model.predict(X_test)                       # integers
le.inverse_transform(preds)                         # 'No' / 'Yes', readable
dict(zip(le.classes_, le.transform(le.classes_)))   # {'No': 0, 'Yes': 1}
```

The order of columns in `predict_proba` follows `model.classes_`, which matches the encoded integer order.

## 5.4 The crucial rule: do NOT use `LabelEncoder` on input features

This is a very common mistake. `LabelEncoder` is designed **only for the target $y$**. scikit-learn's documentation states that it should be used to encode target values, not input features. Reasons:

|Reason|Detail|
|---|---|
|**1D only**|it accepts one column at a time, so it cannot process a 2D feature matrix|
|**No custom order**|it numbers categories alphabetically; for an ordinal feature this produces a **wrong ranking** (Poor above Good)|
|**Does not fit in pipelines**|`fit`/`transform` take only `y`, which clashes with `Pipeline` and `ColumnTransformer`, which call `fit(X, y)` and pass 2D data|
|**One encoder per column**|you would need to manage a separate encoder for each feature by hand and save them all|
|**Implies order for nominal features**|integer codes on a nominal feature invent order (section 2)|

```python
from sklearn.compose import ColumnTransformer

df = pd.DataFrame({"review": ["Good", "Poor", "Average"], "age": [24, 31, 45]})
try:
    ColumnTransformer([("enc", LabelEncoder(), ["review"])]).fit_transform(df)
except Exception as e:
    print(type(e).__name__, ":", str(e)[:80])          # fails: LabelEncoder does not follow the transformer API for X

try:
    LabelEncoder().fit_transform(df[["review", "age"]])     # 2D input
except Exception as e:
    print(type(e).__name__, ":", str(e)[:60])               # y should be a 1d array
```

**Use `OrdinalEncoder` for ordinal features and One-Hot encoding for nominal features. Reserve `LabelEncoder` for $y$.**

## 5.5 Do you even need to encode the target?

Many scikit-learn classifiers accept string labels directly (`LogisticRegression`, `RandomForestClassifier`, and others encode internally and return string predictions). You still encode the target when:

- using **XGBoost** (older versions), **Keras / PyTorch** networks, or any library that requires integer labels,
- you want control over which class is 1,
- you need to compute metrics or custom losses on integers.

## 5.6 Multi-class targets

```python
le = LabelEncoder().fit(["setosa", "versicolor", "virginica", "setosa"])
le.classes_                                   # ['setosa' 'versicolor' 'virginica']  -> 0, 1, 2
```

For multi-class, integer labels carry **no order or distance** for classifiers (they treat each class separately), so label encoding is safe on $y$. This is in contrast to using integer codes on a **feature**. For neural networks with softmax outputs, convert integer labels to one-hot with `keras.utils.to_categorical` or use sparse categorical cross-entropy.

## 5.7 Related tools

|Tool|Use|
|---|---|
|`LabelBinarizer`|label to one-hot/binary matrix for targets|
|`MultiLabelBinarizer`|multi-label targets|
|`pandas.factorize(y, sort=True)`|quick integer codes; returns the uniques|
|`y.map({...})`|explicit mapping with control over the positive class|

# 6. Hands-on workflow: the Customer dataset

The lecture uses a **Customer dataset** with `age`, `gender`, `review`, `education`, and a target `purchased` (Yes/No).

## 6.1 Build the dataset (synthetic stand-in)

```python
import numpy as np
import pandas as pd

rng = np.random.default_rng(42)
n = 200
df = pd.DataFrame({
    "age": rng.integers(18, 61, n),
    "gender": rng.choice(["Male", "Female"], n),
    "review": rng.choice(["Poor", "Average", "Good"], n, p=[0.3, 0.4, 0.3]),
    "education": rng.choice(["School", "UG", "PG"], n, p=[0.3, 0.45, 0.25]),
})
score = (df["review"].map({"Poor": -1.0, "Average": 0.0, "Good": 1.0})
         + df["education"].map({"School": -0.5, "UG": 0.0, "PG": 0.8})
         + (df["age"] - 38) / 25 + rng.normal(0, 0.7, n))
df["purchased"] = np.where(score > 0, "Yes", "No")
print(df.head())
print(df.dtypes)                      # gender, review, education, purchased are object (strings)
```

(Use your own `customer.csv` with `pd.read_csv` if you have it.)

## 6.2 Step 1: identify the features and plan the preprocessing

|Column|Type|Treatment|
|---|---|---|
|`age`|numerical|leave (scale later if needed)|
|`gender`|**nominal**|**One-Hot Encoding** (reserved for the next lesson)|
|`review`|**ordinal** (Poor < Average < Good)|**OrdinalEncoder**|
|`education`|**ordinal** (School < UG < PG)|**OrdinalEncoder**|
|`purchased`|**target** $y$|**LabelEncoder**|

```python
df["purchased"].value_counts(normalize=True)
df.groupby("review")["purchased"].apply(lambda s: (s == "Yes").mean()).reindex(["Poor", "Average", "Good"])
df.groupby("education")["purchased"].apply(lambda s: (s == "Yes").mean()).reindex(["School", "UG", "PG"])
```

The rates should rise with the supposed order, confirming that an ordinal treatment is sensible.

## 6.3 Step 2: split first (prevent data leakage)

```python
from sklearn.model_selection import train_test_split

X = df.drop(columns="purchased")
y = df["purchased"]

X_train, X_test, y_train, y_test = train_test_split(
    X, y, test_size=0.2, random_state=0, stratify=y)
print(X_train.shape, X_test.shape)
```

**Why split before encoding?** Encoders **learn** from data (the set of categories, the mapping). If you fit them on the full dataset, the test set influences preprocessing (data leakage). The rule, as with scalers:

- `fit` on **training data only**
- `transform` both train and test with what was learned
- never `fit` on test

With an **explicit `categories` list**, the ordinal mapping does not depend on the data at all, so leakage is less of a concern, but the habit is essential for every encoder that does learn from data (one-hot, target, frequency encoding), and for unseen-category handling.

## 6.4 Step 3: ordinal encoding for `review` and `education`

```python
from sklearn.preprocessing import OrdinalEncoder

ord_cols = ["review", "education"]
oe = OrdinalEncoder(categories=[
    ["Poor", "Average", "Good"],          # review: lowest to highest
    ["School", "UG", "PG"],               # education: lowest to highest
])

oe.fit(X_train[ord_cols])                                   # learn on TRAIN only
train_ord = oe.transform(X_train[ord_cols])                 # transform TRAIN
test_ord = oe.transform(X_test[ord_cols])                   # transform TEST (same mapping)

print(oe.categories_)
# [array(['Poor', 'Average', 'Good'], dtype=object), array(['School', 'UG', 'PG'], dtype=object)]
```

`fit` learns the mapping from `X_train`; `transform` converts the string columns into integers (Poor 0, Average 1, Good 2; School 0, UG 1, PG 2).

### Put the encoded values back into DataFrames

`OrdinalEncoder` returns a NumPy array, so rebuild a DataFrame:

```python
X_train_enc = X_train.copy()
X_test_enc = X_test.copy()
X_train_enc[ord_cols] = train_ord
X_test_enc[ord_cols] = test_ord
print(X_train_enc.head())
print(X_train_enc[ord_cols].describe().loc[["min", "max"]])        # 0 to 2 for both
```

In scikit-learn 1.2+ you can request DataFrames directly:

```python
oe = OrdinalEncoder(categories=[[...], [...]]).set_output(transform="pandas")
```

### Verify the mapping

```python
check = pd.concat([X_train[ord_cols].reset_index(drop=True),
                   pd.DataFrame(train_ord, columns=[c + "_code" for c in ord_cols])], axis=1)
check.drop_duplicates().sort_values(["review_code", "education_code"]).head(9)
```

Check that "Poor" has code 0 and "Good" code 2, and so on. Always eyeball the mapping once.

## 6.5 Step 4: label encoding for the target `purchased`

```python
from sklearn.preprocessing import LabelEncoder

le = LabelEncoder()
y_train_enc = le.fit_transform(y_train)          # learn the classes on TRAIN labels, then transform
y_test_enc = le.transform(y_test)                # transform TEST labels with the same mapping

print(le.classes_)                               # ['No' 'Yes']
print(y_train_enc[:10])                          # e.g. [0 1 1 0 ...]
```

Targets such as `No` and `Yes` become `0` and `1`.

## 6.6 Step 5: the nominal column (`gender`) is left for One-Hot Encoding

Gender has no order, so it must not be given integer codes. The lecture reserves it for One-Hot Encoding in the next lesson. A preview:

```python
from sklearn.preprocessing import OneHotEncoder

ohe = OneHotEncoder(drop="first", sparse_output=False)       # use sparse=False in scikit-learn < 1.2
gender_train = ohe.fit_transform(X_train[["gender"]])
gender_test = ohe.transform(X_test[["gender"]])
print(ohe.get_feature_names_out())                           # ['gender_Male']  (Female is the reference)
```

`drop="first"` removes one dummy column so the columns are not perfectly collinear (the "dummy variable trap" for linear models). Trees do not need it.

## 6.7 Step 6: the "tedious" part, and the preview of ColumnTransformer

Doing the encodings by hand for different column groups, stitching arrays back together, and repeating for train and test is **tedious and error-prone**. The next lesson introduces `ColumnTransformer` to apply different transformations to different columns in one step. Here is a preview that does everything in this note (plus scaling the numeric `age`) in a single object:

```python
from sklearn.compose import ColumnTransformer
from sklearn.pipeline import Pipeline
from sklearn.preprocessing import StandardScaler
from sklearn.linear_model import LogisticRegression
from sklearn.metrics import accuracy_score

pre = ColumnTransformer(
    transformers=[
        ("ordinal", OrdinalEncoder(categories=[["Poor", "Average", "Good"], ["School", "UG", "PG"]]),
         ["review", "education"]),
        ("nominal", OneHotEncoder(drop="first", handle_unknown="ignore"), ["gender"]),
        ("numeric", StandardScaler(), ["age"]),
    ],
    remainder="drop",
).set_output(transform="pandas")

model = Pipeline([("prep", pre), ("clf", LogisticRegression())])
model.fit(X_train, y_train_enc)                       # the target is label-encoded separately
pred = model.predict(X_test)

print("accuracy:", accuracy_score(y_test_enc, pred).round(3))
print(le.inverse_transform(pred[:5]))                 # readable predictions: 'Yes' / 'No'
print(model[:-1].get_feature_names_out())             # names of the final columns
```

Notice how the three encoders divide the work: **OrdinalEncoder for ordered features, OneHotEncoder for nominal features, LabelEncoder for $y$.** The pipeline guarantees that everything is fitted on the training data only and applied identically to new data.

Cross-validation without leakage:

```python
from sklearn.model_selection import cross_val_score
print(cross_val_score(model, X, (y == "Yes").astype(int), cv=5).mean().round(3))
```

(Here the binary target is encoded by a fixed mapping up front, which cannot leak information. For multi-class targets, fit the label encoder on the full set of class names you know in advance.)

# 7. Experiment: how encoding choices affect models

## 7.1 Ordinal feature: correct order vs alphabetical order

```python
from sklearn.model_selection import cross_val_score
from sklearn.linear_model import LogisticRegression

ord_cols = ["review", "education"]

def make_X(order_aware):
    Xd = X.copy()
    cats = [["Poor", "Average", "Good"], ["School", "UG", "PG"]] if order_aware else "auto"
    Xd[ord_cols] = OrdinalEncoder(categories=cats).fit_transform(Xd[ord_cols])     # demo only: see note below
    Xd["gender"] = (Xd["gender"] == "Male").astype(int)
    return Xd

yy = (y == "Yes").astype(int)
for name, flag in [("alphabetical (wrong)", False), ("custom order (right)", True)]:
    print(f"{name:22s}", cross_val_score(LogisticRegression(max_iter=1000), make_X(flag), yy, cv=5).mean().round(3))
```

(For a quick demonstration only, the encoder is fitted on all rows here. In real work, put it inside a pipeline as in section 6.7.)

With the alphabetical default the order becomes Average < Good < Poor for `review` and PG < School < UG for `education`. A linear model gets a scrambled signal, and accuracy typically drops noticeably compared with the correct order.

## 7.2 Nominal feature: integer codes vs one-hot

Repeat the experiment from section 2.2 on your own data, or compare on a real nominal column such as `state` or `branch`. Typical pattern for a nominal feature with no real order:

|Model|Integer codes|One-hot|
|---|---|---|
|Logistic / linear regression|worse (forced linear effect)|better|
|KNN, SVM|worse (invented distances)|better|
|Random forest, boosted trees|similar (trees can split around the codes)|similar or slightly better|

## 7.3 Checking the "equal spacing" assumption for an ordinal feature

```python
rates = (df.assign(y=(df["purchased"] == "Yes").astype(int))
           .groupby("review")["y"].mean().reindex(["Poor", "Average", "Good"]))
print(rates.round(3))
print("gap Poor->Average:", (rates["Average"] - rates["Poor"]).round(3),
      "| gap Average->Good:", (rates["Good"] - rates["Average"]).round(3))
```

If the two gaps are similar, equal spacing (0, 1, 2) is a good fit; if they differ a lot, consider custom values or one-hot.

# 8. Edge cases

## 8.1 Unknown categories in new data

If the test or production data contains a category never seen when the encoder was fitted (or not in your `categories` list), the default behaviour is an **error**.

```python
oe = OrdinalEncoder(categories=[["Poor", "Average", "Good"]])
oe.fit([["Poor"], ["Good"]])
try:
    oe.transform([["Excellent"]])
except ValueError as e:
    print(str(e)[:80])                       # Found unknown categories ['Excellent'] in column 0 during transform
```

Options:

```python
oe = OrdinalEncoder(categories=[["Poor", "Average", "Good"]],
                    handle_unknown="use_encoded_value", unknown_value=-1)
oe.fit([["Poor"], ["Good"]])
print(oe.transform([["Excellent"]]))         # [[-1.]]

# or np.nan, to be imputed later (tree models such as HistGradientBoosting accept NaN)
OrdinalEncoder(handle_unknown="use_encoded_value", unknown_value=np.nan)
```

Be deliberate: "-1" would look **lower than Poor** to a linear model. If the new category genuinely extends the scale (Excellent above Good), **add it to the `categories` list** and retrain.

## 8.2 Missing values

- In scikit-learn, `OrdinalEncoder` **leaves `NaN` as `NaN`** (missing values are not given a category). Use `encoded_missing_value` to assign a code.
- Many models cannot take NaN. **Impute before encoding** (most frequent value, or a new category "Unknown" if missingness is informative).

```python
from sklearn.impute import SimpleImputer
ord_pipe = Pipeline([
    ("impute", SimpleImputer(strategy="most_frequent")),
    ("encode", OrdinalEncoder(categories=[["Poor", "Average", "Good"]])),
])
```

`LabelEncoder` does **not** accept missing labels. Remove or fix rows with a missing target first.

## 8.3 Dirty strings

Encoders treat `"Good"`, `"good"`, `"Good "` and `"GOOD"` as **different** categories.

```python
for c in ["review", "education"]:
    df[c] = df[c].str.strip().str.title()           # "good " -> "Good"
df["education"] = df["education"].replace({"Under Graduate": "UG", "Post Graduate": "PG", "Ug": "UG", "Pg": "PG"})
sorted(df["education"].unique())                    # check for typos before encoding
```

Always inspect `df[col].unique()` or `value_counts()` first (see [[05.Asking Basic Questions to a Dataset]]).

## 8.4 Rare categories and cardinality

Ordinal columns usually have few categories. For a **high-cardinality nominal** feature (thousands of cities), plain integer codes are meaningless for linear models, and one-hot creates thousands of columns. Better options come in later notes (frequency, target, hashing encoders). In scikit-learn 1.3+ you can group rare levels:

```python
OrdinalEncoder(handle_unknown="use_encoded_value", unknown_value=-1, min_frequency=10)
```

Check which categories exist only in one split:

```python
set(X_test["review"]) - set(X_train["review"])           # categories only in test (would be unknown)
```

With stratified splitting and small datasets, a rare category may land only in the test set. Defining `categories` explicitly from domain knowledge avoids surprises.

## 8.5 Dtype of the result

Output is `float64` by default. Convert if you need integers:

```python
X_train_enc[ord_cols] = X_train_enc[ord_cols].astype(int)        # only if there are no NaN
```

For memory with large data, `dtype=np.int8` is enough for categories with fewer than 128 levels.

## 8.6 Cyclical ordinal data (days, months, hours)

Integer codes create a false gap between the end and the start of the cycle (December = 11 vs January = 0). Use **sine and cosine** features:

```python
month = pd.Series([1, 2, 3, 6, 9, 12])
month_sin = np.sin(2 * np.pi * month / 12)
month_cos = np.cos(2 * np.pi * month / 12)
```

Now December and January are close on the unit circle.

# 10. Choosing an encoder; the road ahead

## 10.1 Ordinal vs Label encoding

|Aspect|**Ordinal Encoding** (`OrdinalEncoder`)|**Label Encoding** (`LabelEncoder`)|
|---|---|---|
|Applies to|**input features** ($X$)|**target variable** ($y$)|
|Input shape|2D (one or many columns)|1D (a single column)|
|Category order|**custom order** via `categories`|alphabetical, automatic, **no custom order**|
|Pipeline / `ColumnTransformer` compatible|yes|no|
|Unknown categories|`handle_unknown` option|error|
|Output|integers $0 \dots K-1$ per column (as floats)|integers $0 \dots K-1$|
|Typical use|education, rating, size, grade|purchased Yes/No, species, churn|
|Common mistake|forgetting `categories` (alphabetical order)|applying it to $X$|

## 10.2 Which encoder for which data

|Data|First choice|Notes|
|---|---|---|
|Ordinal feature|**OrdinalEncoder** with explicit order|check spacing|
|Nominal feature, low cardinality (about 2 to 15)|**One-Hot Encoding**|next lesson|
|Nominal feature, high cardinality|frequency, target, hashing, or native categorical support|later notes|
|Binary feature (Yes/No, Male/Female)|map to 0/1 (or one-hot with `drop="first"`)||
|Cyclical (hour, month, weekday)|sine/cosine||
|Target label|**LabelEncoder** (or explicit map)|only if the library needs it|
|Tree model, quick baseline|ordinal codes may work for nominal columns|tell the model they are categorical|

## 10.3 The road ahead

1. **One-Hot Encoding** for nominal variables such as `gender`, `state`, and `branch`: one binary column per category.
2. **`ColumnTransformer`** to apply different encoders and scalers to different columns in one object, with correct train/test handling.
3. Later: **frequency/count encoding, target (mean) encoding, binary encoding, hashing**, and rare-label handling for high-cardinality columns.

# 11. Reference and practice

## 11.1 Common mistakes

|Mistake|Consequence|Fix|
|---|---|---|
|`LabelEncoder` on input features|alphabetical order, 1D only, breaks pipelines|`OrdinalEncoder` / One-Hot for $X$|
|`OrdinalEncoder()` without `categories` on an ordinal column|alphabetical order scrambles the ranking|pass the explicit order|
|Integer codes on a nominal feature (linear / distance models)|invented order and distances|One-Hot|
|Misaligned `categories` list vs column order|silently wrong encoding|select columns explicitly, keep order aligned|
|Fitting the encoder before the split|data leakage|split first, fit on train|
|`fit_transform` on the test set|different mappings per split|`transform` only|
|Ignoring unseen categories|crash in production|`handle_unknown`, or define all levels|
|Dirty strings ("good", "Good ")|duplicate categories|clean (`str.strip().str.title()`)|
|Missing values left in|NaN errors in models|impute before encoding|
|Alphabetical label order flips the positive class|precision/recall about the wrong class|explicit mapping or `pos_label`|
|Assuming equal spacing blindly|misleading linear effects|check target rates, use custom values or one-hot|
|Using plain ordinal codes for cyclical features|false distance between the end and start|sin/cos|
|Treating ID-like numbers (`pincode`) as numeric|meaningless order|treat as nominal|
|Forgetting to save the encoders|cannot reproduce or decode predictions|`joblib.dump`|

### Short answers

1. Algorithms compute with numbers (distances, gradients, dot products); strings must be converted.
2. Nominal has no order (state, gender); ordinal has a natural rank (education, rating, size).
3. Integers impose a fake order, equal spacing, and distances (a single forced linear effect).
4. It sets the exact order of categories per column: a list of lists, one inner list per column, ordered low to high, matching the column order.
5. Alphabetical (sorted) order, which usually is not the real ranking.
6. The target $y$. On features it is 1D only, has no custom order, and does not work in pipelines or `ColumnTransformer`.
7. Encoders learn from data; fitting on all of it leaks test information into preprocessing.
8. `fit` learns the mapping, `transform` applies it, `fit_transform` does both (training data only).
9. `handle_unknown="use_encoded_value"` with `unknown_value`, add the category to `categories`, or retrain.
10. The class that sorts last becomes 1 (the "positive" class), which may be the wrong class to detect.
11. One-Hot Encoding, because gender is nominal with no order.
12. Applying different preprocessing steps to different columns in one fitted, leakage-safe object.
13. They are cyclical: December and January are adjacent in time but far apart as integers; use sin/cos.
14. Compare the target rate per category and see whether the gaps are roughly equal.

## 11.5 Glossary

|Term|Meaning|
|---|---|
|**Categorical variable**|takes values from a limited set of categories|
|**Nominal**|categories with no order|
|**Ordinal**|categories with a natural order|
|**Encoding**|converting categories to numbers|
|**Ordinal Encoding**|mapping ordered categories to integers that respect the order|
|**Label Encoding**|mapping target classes to integers $0 \dots K-1$|
|**One-Hot Encoding**|one binary column per category|
|**Cardinality**|number of distinct categories|
|**Reference category**|the dropped dummy in one-hot with `drop="first"`|
|**Dummy variable trap**|perfect collinearity when all K dummies and an intercept are used|
|**Data leakage**|test information influencing training or preprocessing|
|**Unknown category**|a category not seen when the encoder was fitted|
|**Cyclical feature**|a feature whose end connects to its start (hours, months)|

## Key takeaways

- Models need **numbers**, so categorical strings must be **encoded**. The goal is to add **no fake information** (invented order or distances) and keep **real information** (true order).
- **Nominal** data has no order (state, branch, gender); **ordinal** data has a natural rank (education, rating, size). Nominal features need One-Hot Encoding; ordinal features need **Ordinal Encoding**.
- **`OrdinalEncoder`** is for **input features $X$**, works on 2D data, and accepts a **custom order** through `categories` (a list of lists, lowest to highest, aligned with the column order). Without it, the default is **alphabetical**, which scrambles the ranking.
- **`LabelEncoder`** is for the **target $y$ only**: 1D, automatic alphabetical codes from 0 to K-1, no custom order, not usable in pipelines. Using it on features is a classic mistake that scikit-learn's own documentation warns against. Check which class becomes 1.
- Workflow from the lecture's customer dataset: `gender` (nominal) goes to One-Hot, `review` and `education` (ordinal) go to `OrdinalEncoder` with `['Poor', 'Average', 'Good']` and `['School', 'UG', 'PG']`, and `purchased` (target) goes to `LabelEncoder`.
- **Split first, fit on training data only**, then transform train and test, to avoid data leakage. Handle unknown categories, missing values, and dirty strings deliberately.
- Applying different encoders by hand is tedious; the next lesson introduces **One-Hot Encoding** and **`ColumnTransformer`** to do it all in a single, leakage-safe pipeline.
